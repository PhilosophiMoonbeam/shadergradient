# Native Svelte support: assessment and delivery contract

Assessment date: 2026-10-28. Source baseline: `785dcd4` on branch `svelte`.

## Decision and scope

**Proceed as an upstream-additive native adapter:** add `@shadergradient/svelte` using Svelte 5 and Threlte 8, and introduce a small public `@shadergradient/core` for framework-neutral assets. Preserve existing React, Vue, Next, Nuxt, Framer and Figma behavior. This is an assessment and executable delivery plan, not an implemented Svelte package or a claim of full parity.

The upstream precedent is concrete: [PR #160](https://github.com/ruucm/shadergradient/pull/160), “feat(vue): add Vue 3 and Nuxt support,” merged on 2026-09-23; merge `894f9a1` is present in this checkout's history. The orchestrator checked the [GitHub API record](https://api.github.com/repos/ruucm/shadergradient/pulls/160) and registry: [`@shadergradient/vue/latest`](https://registry.npmjs.org/@shadergradient/vue/latest) is published as `0.1.0`; [`@shadergradient/react/latest`](https://registry.npmjs.org/@shadergradient/react/latest) is `2.4.20`, while this checkout's React manifest is `2.4.24`. Vue is not an unpublished fork experiment. The stale publication sentence in `CONTRIBUTING-VUE.md:5-6` is not authority for registry state; repairing unrelated publication documentation is outside this assessment.

Existing support includes React/React Three Fiber consumers (Next and Vite), Vue/Tres consumers including Nuxt SSR, and React-oriented Framer/Figma tooling. The repository documents these at `README.md:20-26,48-76,172-182`; React's public exports include Framer controls (`packages/shadergradient/src/index.ts:1-6`). This does not establish additional runtime adapters such as Webflow or Wix.

The completed epic includes all four native primitives—`ShaderGradientCanvas`, `ShaderGradient`, `ShaderGradientSource`, `ShaderGradientView`—plus explicit source handles, real workspace and standalone consumers, tests, documentation and release preparation. Source/View is required, not an optional follow-up. No automatic implementation commits, pushes, publication, or remote Beads/Dolt synchronization are authorized.

## Architecture options and selected boundaries

| Option                                   | Assessment                                                                                                                                                                               |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Native Svelte 5 + Threlte 8              | **Selected.** Supports ordinary Svelte snippets/context, existing Threlte scene composition, ordered scheduler tasks and explicit ownership while reusing the current WebGL/GLSL output. |
| Standalone direct-Three renderer         | Technically possible, but duplicates sizing, scheduling, context and disposal machinery. No demonstrated requirement justifies a second renderer backend.                                |
| Svelte wrapper mounting React/R3F        | A bridge, not native support. Adds React lifecycle/runtime requirements and cannot provide ordinary native Threlte children. Excluded.                                                   |
| Svelte-specific copy of all shaders/data | Avoids immediate extraction but creates a third divergent asset tree. Excluded in favor of public pure core.                                                                             |

Package `packages/shadergradient-svelte` uses `@sveltejs/package`, shipping preprocessed `.svelte` components, transpiled helper modules and generated declarations with `types`/`svelte` export conditions. Use correct CSS side-effect declarations and fully specified runtime import paths. This follows [official packaging guidance](https://svelte.dev/docs/kit/packaging), not Vue's JS-only tsup publication format. Kit is a consumer and SSR-test environment only: the library has no `$app/*` runtime dependency, and plain Svelte/Vite is a first-class consumer.

### Public native API and context

F01 records exact exported names/types and callback payloads before implementation. The selected surface is:

- `ShaderGradientCanvas`: HTML wrapper and owned Threlte renderer; `pixelDensity`, `fov`, `pointerEvents`, `envBasePath`, `lazyLoad`, `threshold`, `rootMargin`, `preserveDrawingBuffer`, `powerPreference`; typed `children` and `fallback` snippets; outer HTML attributes, `class`, `style`. Document required nonzero layout dimensions. Default decorative `aria-hidden` and pointer noninterception are overridable for meaningful images and accessible controls. Failure states are `deferred`, `loading`, `unsupported`, `error`, never a false “loaded.”
- `ShaderGradient`: in-Canvas primitive with discriminated `mode: 'managed' | 'external'`, typed native visual/query/time settings, `onCameraUpdate` and `onError` callback props. Managed mode owns one scene-wide camera/environment/controls/grain pipeline. External mode owns mesh/material/animation only, excludes managed-only settings in its types, and supports several gradients under an existing consumer Threlte Canvas. Missing context and duplicate managed ownership raise actionable errors.
- `createGradientSource` / `GradientSourceHandle` and `ShaderGradientSource` / `ShaderGradientView`: explicit producer/view sharing detailed below. Final declaration spelling and helper export partition are frozen by F01 and validated by consumer type tests, not improvised independently in component tasks.
- Narrow public types cover shader/geometry unions, normalized settings, Canvas props/fallback states, managed/external settings, camera callback payload and source handle state. Do not re-export React's permissive prop bag as the native API.

Canvas-provided settings context and per-scene ownership context are separate responsibilities. A Canvas wrapper cannot call descendant Threlte hooks before it provides that context; scene helpers initialize beneath the actual Threlte Canvas. Typed Svelte context scopes reactive configuration, invalidation and ownership registration per tree, never renderer-disposal ownership or a module-global scene registry. See [Svelte context](https://svelte.dev/docs/svelte/context), [SSR state isolation](https://svelte.dev/docs/kit/state-management), and [Threlte Canvas context/layout](https://threlte.xyz/docs/reference/core/canvas/).

F01 freezes the internal handoff as well as the public API: `CanvasLifecycleContext` supplies live settings/motion/canvas reference, ownership, invalidation and post-render subscription; `MeshHandle` supplies stable material/uniform/time access; scene registration is scoped to the actual Threlte scene. Camera, Lights, Grain and Axes expose explicit setup/cleanup handles. Required order is controls → uniform/time updates → one default render or composer replacement → completed-frame subscribers. Source handles use producer tokens, generation-checked frame publication and visible-view demand; no helper silently assumes renderer ownership.

Under a consumer-owned Threlte Canvas, absent package Canvas context resolves neutral environment/motion settings locally; it does not create a global mutable fallback or acquire renderer ownership. A paused View resize obtains a scheduled source-frame lease before copying, rather than assuming an old drawing buffer remains readable.

### SSR and hydration contract

Importing through Svelte-aware tooling and rendering the library server-side must not construct WebGL, touch browser globals/observers or start HDR requests. Server HTML and first hydration output preserve a stable wrapper/fallback. An explicit client mount boundary prevents rendering browser scene snippets or constructing the Canvas before mount; disabling page SSR is not an acceptable workaround. Async loading after unmount must not mount a stale scene or publish stale resources.

A raw Node ESM import of pure core is a separate gate from a Svelte-compiled SSR import of components. Raw Node is not promised to execute uncompiled `.svelte` files. Concurrent requests and independent trees must have isolated handles, settings and ownership state. SSR import safety alone is not hydration, navigation or browser rendering proof.

### Scheduling, reactivity and resource ownership

Use one Threlte scheduler per Canvas. Time/control tasks precede rendering; grain replaces the default render task instead of adding a second render; source copies follow completed source rendering. Stop temporal tasks or conditional invalidation when paused/reduced-motion/offscreen; `useTask` automatically invalidates unless configured otherwise, so merely freezing a uniform is not sufficient. Explicit settings, camera input, resize, HDR completion and time seeks still invalidate. [Official `useTask` documentation](https://threlte.xyz/docs/reference/core/use-task/) describes task ordering, `running`, `autoInvalidate` and custom render-stage ownership.

Keep Three objects and uniform containers in ordinary variables or `$state.raw` when replacement must be reactive. No per-frame Color/Vector/array allocation, URL parsing, object replacement or Svelte UI-state churn. Change uniforms/transforms in place; rebuild geometry only for topology changes and materials only when variant changes require it.

Canvas owns renderer/context cleanup. Gradient owns its geometry/material/helpers/controls and owned asset handles. Grain owns its passes/targets. Host-owned renderer, camera, environment and materials are never disposed by an external gradient. Choose explicit or Threlte automatic disposal for each resource, not both; Threlte only automatically disposes objects referenced through `<T>`, not every attached texture. Late HDR results are disposed; restoration checks that the environment is still the one assigned by this owner. See [official disposal limitations](https://threlte.xyz/docs/learn/basics/disposing-objects/).

For the selected Three `0.186.1` revision, a native material also owns one DFG lookup texture clone. Three assigns a module-shared `DFG_LUT` during physical-material refresh; uploading that borrowed texture leaves renderer-retaining disposal listeners on the shared object. The native [material hook](https://threejs.org/docs/pages/Material.html) supplies a stable uniform binding whose [texture clone](https://threejs.org/docs/pages/Texture.html) shares the unchanged pixel Source and is reused across frames. Material teardown disposes only that owned clone. It never disposes the shared lookup, a host texture or the renderer, and introduces no global registry, shader-chunk mutation or shared-core material factory.

### Required Source/View contract

Create a `GradientSourceHandle` per component/app tree and explicitly pass it to one Source and any number of Views. No global string IDs, cached map entries or server-global handle. Its lifecycle distinguishes absent producer, producer loading, completed/ready frame, error and teardown; generation ownership prevents late producer completion from reviving a released source. Views may exist before Source. Duplicate producers fail deterministically; reactive handle replacement unsubscribes and rebinds; teardown clears readiness and stale pixels without affecting unrelated handles.

Source owns one renderer. Views are 2D mirrors with centered cover cropping, bounded source/view DPR and resolution, resize recopy while paused, and no independent camera-interaction promise. Copy only after completed source frames or required resize/visibility updates; offscreen views do not copy. The producer responds to visible subscriber demand and does not remain permanently active just because its hidden element intersects a viewport. Removing the last visible subscriber or unmounting must release subscriptions and stop unnecessary work. Copies use the same scheduler, not an independent perpetual RAF. Enable `preserveDrawingBuffer` only if measured copy-phase behavior requires it; Vue's unconditional choice (`ShaderGradientSource.ts:63-72`) is not evidence that native post-render copying needs it.

## Version and toolchain policy

Registry existence is not compatibility proof. Current candidate pins are Svelte `5.57.3`, Threlte `8.6.1`, Three `0.186.1`; the disposable native probe actually used Svelte **`5.57.1`**, Threlte **`8.6.1`**, Three **`0.186.1`**, Vite **`8.2.1`**, vite-plugin-svelte **`7.3.0`**. Do not relabel that as testing `5.57.3`.

- Proposed Svelte peer floor is `>=5.40 <6` when using `createContext`, introduced in 5.40 per [official context docs](https://svelte.dev/docs/svelte/context). F03 must demonstrate lower-bound and current consumers before freezing that floor.
- Threlte 8 is the selected adapter major. Its published peer declaration does not establish compatibility of every ShaderGradient variant with every accepted Three revision. [Registry metadata](https://registry.npmjs.org/@threlte/core/latest) reports `8.6.1`; test actual lower/current combinations.
- Bound Three peers by demonstrated shader/chunk/material/addon behavior. Do not inherit Vue's `>=0.180.0` declaration as a native tested range. Legacy include removal, luminance replacements, physical transmission, color management and composer render-target behavior are concrete revision-sensitive risks.
- Existing React declares Three `>=0.150.0` and develops against `^0.169.0` (`packages/shadergradient/package.json:28-33,50`); Vue declares `>=0.180.0` and develops against `^0.186.0` (`packages/shadergradient-vue/package.json:25-38`). Preserve those adapters' bounds and behavior unless their own baseline exposes a specifically scoped blocker.
- [Kit `3.1.0` metadata](https://registry.npmjs.org/@sveltejs/kit/3.1.0) requires Node `>=22.17`, Vite `^8.0.12`, Svelte `^5.57.1`, plugin `^7.0.0`, and optional TypeScript `^6.0.0`. Scope this toolchain to new consumers/package needs; do not blanket-upgrade root TypeScript `5.7.3`, old React Three or the root Node engine (`package.json:29-35`). Kit is not a runtime peer of the library.
- Root pnpm is `10.12.4`; workspace patterns include only immediate `apps/*` and `packages/*` (`package.json:31`; `pnpm-workspace.yaml:1-3`). Nested standalone examples require their own lockfiles/config and real packed-package installs, not invisible workspace-link success.
- No mandatory React, R3F, `@threlte/extras`, Skeleton, physics, XR, Theatre or WebGPU/TSL dependency is needed. Preserve WebGL and current GLSL.
